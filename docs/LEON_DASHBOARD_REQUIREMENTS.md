# Leon Dashboard Requirements

This document captures the functional and non-functional requirements for the Leon operational task dashboard.

## Purpose

The dashboard is the source of truth for all work issued to Leon (the assistant) and its sub-agents. It should allow Sridhar to see what Leon is working on, what has been completed, what failed, and why.

## Core Entities

- **Task**
  - Represents a unit of work assigned to Leon or a sub-agent.
  - Key fields:
    - `id` – unique identifier (string, generated by the system or provided by the caller).
    - `project` – optional logical grouping (e.g., `echolyne`, `leon-dashboard`, `chc-ltss`).
    - `category` – area or domain (e.g., `DevOps`, `Healthcare`, `Personal`).
    - `summary` – short human-readable description.
    - `description` – longer description / acceptance criteria.
    - `status` – one of `Not Started`, `In Progress`, `Completed`, `Cancelled`, `On Hold`.
    - `created_at` – unix timestamp (ms) when the task was created.
    - `completed_at` – unix timestamp (ms) when the task reached a terminal status (usually `Completed`).
    - `reason` – explanation for `Cancelled` / `On Hold`.
    - `additional_comments` – free-form notes.

## Functional Requirements

### Task Capture

1. Create new tasks via HTTP API.
2. Optional ability to specify `id` (for external systems that want stable IDs); otherwise auto-generate.
3. Optional `project` field on creation; may be empty/undefined.
4. Default `status` to `Not Started` when not specified.

### Task Viewing

1. `/tasks` page shows a list of tasks with:
   - `id`, `project`, `category`, `summary`, `status`, `created_at`, `completed_at`, `reason`, `additional_comments`.
2. Tasks are ordered by `created_at` descending.
3. Filters:
   - by `status` (All + each status value),
   - by `category` (All + discovered categories),
   - by `project` (All + discovered projects).

### Task Creation (UI)

1. `/tasks` provides a modal form to create a task.
2. Required fields: `category`, `summary`.
3. Optional fields: `project`, `description`, `status`, `additional_comments`.
4. On successful creation, the UI refreshes the task list and metrics.

### Task Updates

1. Backend API supports updating:
   - `status`, `completed_at`, `reason`, `additional_comments`.
2. When `status` transitions to `Completed` and `completed_at` is not supplied, the system auto-populates `completed_at` with the current time.
3. When `status` transitions away from `Completed`, `completed_at` is cleared unless explicitly set.
4. Update route is exposed at `/api/tasks/[id]/update`.
5. (Future) UI may expose status updates; for now the route is available for programmatic use by Leon/sub-agents.

### Metrics

1. `/api/tasks/metrics` returns:
   - `total` tasks.
   - `byStatus` counts.
   - `byCategory` counts.
   - `completionRate` (% of tasks with `status = Completed`).
   - `failureRate` (% of tasks with `status = Cancelled`).
   - `last7Days` – tasks created in last 7 days.
   - `last30Days` – tasks created in last 30 days.
2. (Future) Metrics may be extended to include per-project breakdowns.

## Non-Functional Requirements

- **Storage:** SQLite (`data/tasks.db`) via `better-sqlite3`.
- **Migration:** The app should gracefully handle startup against an existing DB by applying non-destructive schema changes (e.g., adding new columns).
- **Security:**
  - The dashboard is fronted by OAuth2 proxy (GitHub/Google) and an approval step.
  - Only approved users should see the dashboard.
- **Simplicity:**
  - Keep the schema and UI minimal and pragmatic.
  - Prefer clear, explicit fields over premature generalisation.

## Out of Scope (for now)

- Complex workflow states beyond the defined `TaskStatus` values.
- Subtask hierarchies / dependencies.
- Full-text search.
- Multi-tenant separation beyond the `project` and `category` fields.
